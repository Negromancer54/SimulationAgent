# SimulationAgent — контракт V0.X–V1 и переход к Task V2

**Назначение:** восстановить архитектурный контракт раннего развития SimulationAgent и зафиксировать переход от низкоуровневого транзакционного механизма к структурированному Task API.

**Хронологическая область:** V0.X → V0.3 → V0.3.1 → V0.4 → TaskResult V1 → Task V1 → Task V2.

---

# 1. Назначение раннего SimulationAgent

SimulationAgent создавался не как часть SimulationZero, а как внешний локальный исполнитель для разработки SimulationZero-Cpp.

Базовая идея:

```text
Human / GPT
     ↓
SimulationAgent
     ↓
Filesystem / Git / Build / Run
```

Agent должен уметь:

* читать проект;
* искать файлы и содержимое;
* создавать и изменять файлы;
* контролировать Git;
* запускать сборку;
* запускать программу/тесты;
* получать диагностические данные;
* безопасно откатывать изменения.

При этом ранний Agent не должен самостоятельно принимать архитектурные решения проекта.

Он является **исполнительным слоем**, а не заменой разработчику/GPT.

---

# 2. V0.X — базовый безопасный исполнитель

Первая архитектурная стадия была сосредоточена на безопасных примитивах.

Agent должен ограничивать:

* область файловых операций;
* доступ к проекту;
* возможность выхода за пределы project root;
* возможность случайно изменить build/output;
* разрушительные операции;
* работу с Git.

Основной принцип:

> Любая автоматическая операция должна быть ограничена и проверяема.

---

# 3. Безопасное изменение файлов

Для раннего Agent базовой операцией изменения стала контролируемая текстовая замена.

Основные гарантии:

```text
relative path
      ↓
project-root containment
      ↓
exact text match
      ↓
expected occurrence count
      ↓
replace
```

Для `replace`:

```text
expected_count == actual_count
        ↓
      replace
```

Если:

```text
actual != expected
```

изменение не выполняется.

Следовательно:

```text
0 вместо 1   → ABORT
2 вместо 1   → ABORT
1 вместо 1   → REPLACE
```

Это стало фундаментальным принципом безопасной автоматизации:

> Agent не должен изменять файл, если фактическое состояние не совпадает с его предположением.

---

# 4. Git как механизм контроля состояния

Agent начал использовать Git не только как систему версий, но и как механизм проверки состояния рабочей области.

Базовые операции:

```text
git status
git diff
checkpoint
rollback
```

Перед автоматическим изменением требовалось проверить рабочее дерево.

Основное правило:

```text
working tree != clean
        ↓
       STOP
```

Agent не должен начинать транзакционную задачу поверх неизвестных чужих изменений.

---

# 5. V0.3 — checkpoint / rollback

Следующим важным этапом стало появление контрольной точки.

Первоначальная модель checkpoint была связана с текущим процессом Agent, но затем была признана недостаточной.

Проблема:

> состояние безопасности не должно исчезать при перезапуске Python-процесса.

---

# 6. V0.3.1 — persistent checkpoint

Checkpoint был перенесён в постоянное состояние на диске.

Концептуально:

```text
SimulationAgent
└── state
    └── checkpoint
```

Checkpoint должен сохранять исходную Git-точку, позволяющую восстановить проект после неудачной транзакции.

Таким образом:

```text
checkpoint
    =
externalized transaction baseline
```

Ключевой принцип:

> безопасность не должна зависеть от времени жизни процесса Agent.

---

# 7. Baseline проекта

Для SimulationZero-Cpp был создан Git baseline.

Ключевая идея раннего Agent:

```text
known clean state
        ↓
task
        ↓
verification
```

После начала автоматической задачи Agent должен иметь возможность доказать, от какого состояния он начинал работу.

---

# 8. V0.4 — переход от операций к транзакции

Следующее фундаментальное изменение состояло в том, что Agent перестал рассматриваться как набор отдельных действий.

Вместо:

```text
write_file()
replace_file()
build()
run()
```

появился единый **transactional task cycle**.

Основной pipeline:

```text
TASK
  ↓
PRECHECK
  ↓
CHECKPOINT
  ↓
EDIT
  ↓
DIFF
  ↓
DIFF VALIDATION
  ↓
BUILD
  ↓
RUN
  ↓
PASS / ROLLBACK
```

Это стало основным execution-контрактом V0.4.

---

# 9. PRECHECK

Перед началом задачи Agent проверяет возможность безопасного запуска.

Минимально:

```text
repository exists
working tree clean
task can be started
```

Failure на этой стадии означает:

```text
no checkpoint
no mutation
no execution
```

---

# 10. CHECKPOINT

Если PRECHECK успешен, создаётся checkpoint.

С этого момента начинается транзакционная часть задачи.

Инвариант:

> После создания checkpoint Agent должен иметь возможность восстановить исходное состояние проекта в случае failure.

---

# 11. EDIT

На стадии EDIT Agent выполняет предусмотренные изменения.

Каждое изменение должно использовать безопасный primitive.

На этом этапе не разрешается:

* молча менять дополнительные файлы;
* игнорировать mismatch;
* продолжать после неудачной операции.

Любой edit failure прекращает нормальное выполнение задачи.

---

# 12. DIFF

После изменения Agent получает фактическое состояние Git diff.

DIFF используется для ответа на вопрос:

> Что на самом деле было изменено?

Это принципиально отделено от предположения о том, что Agent хотел изменить.

---

# 13. DIFF VALIDATION

Следующая проверка отвечает на вопрос:

> Соответствуют ли фактические изменения ожидаемому контракту задачи?

На раннем этапе это было связано с `expected_paths`.

Идея:

```text
expected_paths
        ↕
actual changed paths
```

Несоответствие должно приводить к отказу и rollback.

---

# 14. BUILD

После успешных EDIT и DIFF validation Agent запускает сборку проекта.

Build failure:

```text
BUILD FAILED
      ↓
ROLLBACK
```

Сама сборка является частью транзакции, а не внешней ручной процедурой.

---

# 15. RUN

После успешной сборки Agent запускает исполняемый файл/тесты.

Run failure также является транзакционным failure:

```text
RUN FAILED
      ↓
ROLLBACK
```

Следовательно, успешное изменение файлов само по себе не означает успешную Task.

---

# 16. ROLLBACK

Rollback является не аварийной вспомогательной функцией, а частью основного контракта.

При failure после checkpoint:

```text
failure
   ↓
rollback
   ↓
verify restored state
```

Основной инвариант:

> неуспешная задача не должна оставлять после себя частично применённый результат.

---

# 17. Rollback failure

Отдельно была выделена опасная ситуация:

```text
Task FAILED
      +
ROLLBACK FAILED
```

В таком случае проект нельзя считать безопасно восстановленным.

Поэтому rollback failure является специальным состоянием.

Позже оно стало:

```text
ROLLBACK_FAILED
```

с отдельной фиксацией результата rollback.

---

# 18. TaskResult V1

После стабилизации transactional pipeline появился единый структурированный результат.

`TaskResult` должен отвечать на вопросы:

* была ли задача успешна;
* на какой стадии она завершилась;
* какой checkpoint использовался;
* какие edits были выполнены;
* какой diff получен;
* прошла ли diff validation;
* как завершилась build;
* как завершился run;
* выполнялся ли rollback;
* произошёл ли rollback failure;
* какие diagnostics доступны.

Концептуально:

```text
TaskResult
├── success
├── stage
├── attempts
├── checkpoint
├── edits
├── diff
├── build
├── run
├── rollback
├── failure
└── diagnostics
```

---

# 19. JSON-контракт TaskResult

TaskResult получил машинно-читаемое JSON-представление.

Базовый корневой контракт включал:

```text
schema_version
success
stage
attempts
checkpoint
edits
diff
build
run
rollback
failure
diagnostics
```

Это было сделано для будущего взаимодействия:

```text
GPT
 ↕
SimulationAgent
```

и позже стало основой Bridge-интеграции.

---

# 20. Разделение stage и failure

Было принято важное концептуальное разделение.

`stage` отвечает:

> где закончился pipeline?

`failure_code` отвечает:

> почему он закончился неуспешно?

Например:

```text
stage = ROLLBACK
failure_code = BUILD_FAILED
```

а при невозможности отката:

```text
stage = FAILED
failure_code = ROLLBACK_FAILED
```

Эти понятия нельзя смешивать.

---

# 21. Единая функция fail_task()

Для failure paths был выделен единый механизм завершения неудачной задачи.

Он должен:

```text
record original failure
        ↓
attempt rollback when applicable
        ↓
return final TaskResult
```

При успешном rollback исходная причина сохраняется.

При rollback failure итоговый failure становится:

```text
ROLLBACK_FAILED
```

---

# 22. Ограничение автономии

На V0.X–V1 Agent не должен самостоятельно решать:

* менять архитектуру;
* удалять существующие тесты;
* ослаблять assertions;
* модифицировать build;
* принимать неожиданные изменения;
* считать задачу успешной без проверки.

Отсюда позднее возникла идея:

```text
L0 READ ONLY
L1 SAFE FIX
L2 TASK IMPLEMENTATION
L3 AUTONOMOUS STAGE
L4 ARCHITECTURAL
```

Но сами уровни автономии на этом этапе являлись скорее рамкой будущего Agent, чем полностью реализованной системой.

---

# 23. Task V1 — от операций к объекту задачи

Следующим шагом стало отделение:

```text
what to execute
```

от:

```text
how to execute
```

Вместо API вида:

```text
run_task(edits, expected_paths)
```

появился объект:

```text
Task
├── edits
└── expected_paths
```

А вызов:

```text
run_task(task)
```

стал новой формой execution API.

Основной принцип:

> `Task` описывает задачу; `run_task()` исполняет её.

---

# 24. Execution Contract V1

После появления `Task` архитектура стала:

```text
Task
   ↓
run_task()
   ↓
TaskResult
```

Это было первое явное разделение входного контракта и результата транзакции.

`TaskResult` при этом оставался отдельным контрактом.

---

# 25. Почему Task V1 оказался недостаточным

У Task V1 была принципиальная слабость:

```text
Task
├── edits
└── expected_paths
```

Он описывал преимущественно **низкоуровневые изменения**, но почти ничего не говорил о намерении человека или GPT.

Agent фактически получал:

> какие изменения выполнить,

но не получал формального:

> какую задачу эти изменения реализуют.

Кроме того, существовал соблазн передавать неполные Task.

Поэтому V1 постепенно был признан переходной моделью.

---

# 26. Task V2 — structured external task

На следующем этапе `Task` был расширен до:

```text
Task V2
├── task_id
├── description
├── edits
└── expected_paths
```

### task_id

Обязательная непустая строка.

Назначение:

* идентификация задачи;
* корреляция во внешнем API;
* будущая интеграция с Bridge/orchestration.

### description

Обязательная непустая строка.

Назначение:

* человеческое описание;
* контекст для GPT/Agent;
* идентификация смысла задачи на внешнем уровне.

На V2 `description` ещё не являлся формальной машиночитаемой семантикой.

---

# 27. Edit contract V2

Поддерживаются два вида операций.

## CREATE

```text
type = create
path      : non-empty string
content   : string
```

Пустой `content` допустим.

То есть создание пустого файла является валидной операцией.

---

## REPLACE

```text
type = replace
path            : non-empty string
old_text        : non-empty string
new_text        : string
expected_count  : optional positive integer
```

При этом:

```text
bool
```

не является допустимым `expected_count`, несмотря на то что `bool` является подклассом `int` в Python.

Пустой `new_text` допустим.

---

# 28. Multiple edits

V2 явно разрешил составные задачи.

Допустимы:

```text
multiple creates
multiple replaces
multiple edits
```

В том числе:

```text
same path
```

и:

```text
create
  ↓
replace
```

на одном пути.

Это позволило рассматривать Task как **транзакцию над последовательностью изменений**, а не одну операцию.

---

# 29. expected_paths V2

`expected_paths` был формализован как path oracle.

Когда список задан:

```text
set(edit paths)
    ==
set(expected_paths)
```

Это означает, что фактическое множество изменённых путей должно соответствовать декларации.

При этом порядок путей не имеет значения.

---

# 30. Пустой expected_paths

В процессе стабилизации было найдено противоречие между validate_task() и run_task().

Итоговый V2-контракт:

```text
expected_paths = []
```

означает:

> path oracle не объявлен.

Это не ошибка.

В таком случае:

```text
EDIT
 ↓
DIFF
 ↓
collect changed paths
 ↓
skip DIFF path validation
 ↓
BUILD
 ↓
RUN
```

При этом:

```text
diff_validated = True
```

несмотря на отсутствие path comparison.

---

# 31. Validation Task V2

`validate_task()` был выделен в отдельный контрактный слой.

Он проверяет:

```text
Task
├── task_id
├── description
├── edits
└── expected_paths
```

а затем проверяет содержимое `edits`.

Контракт включает:

* тип контейнеров;
* наличие обязательных полей;
* типы полей;
* допустимые edit types;
* непустые path;
* допустимость пустого content;
* корректность expected_count;
* корректность expected_paths;
* согласованность expected_paths и edits, когда oracle задан.

---

# 32. Разделение validation и execution

На V2 окончательно закрепилась граница:

```text
Task
 ↓
validate_task()
 ↓
run_task()
```

Если Task структурно невалиден:

```text
validation failure
        ↓
no checkpoint
no mutation
no build
no run
```

То есть структурная ошибка не является частично выполненной транзакцией.

---

# 33. Multi-edit transaction

V2 подтвердил, что все edits одной Task образуют единую транзакцию.

Например:

```text
EDIT 1 → SUCCESS
EDIT 2 → SUCCESS
EDIT 3 → FAILURE
```

результат:

```text
EDIT_FAILED
      ↓
ROLLBACK ALL
```

а не:

```text
ROLLBACK ONLY EDIT 3
```

Таким образом:

> Task является атомарной единицей транзакции.

---

# 34. Составные успешные Task

Были подтверждены сценарии:

```text
multiple create
multiple replace
create + replace different paths
create + replace same path
```

Причём изменения применяются последовательно внутри одной транзакции.

Особенно важен случай:

```text
create file
     ↓
replace same file
```

Второй edit действительно работает с состоянием, созданным первым edit.

---

# 35. Rollback составной Task

При failure внутри составной Task:

```text
successful edits before failure
        ↓
rollback
        ↓
all previous changes removed
```

Для созданных файлов они должны исчезнуть.

Для изменённых файлов исходное содержимое должно восстановиться.

Таким образом, V2 закрепляет **transactional atomicity на уровне всей Task**.

---

# 36. Task V2 и TaskResult V1

Одним из принципиальных решений стало отсутствие необходимости создавать новую версию TaskResult только из-за появления Task V2.

Получилось:

```text
Task V2
   ↓
run_task()
   ↓
TaskResult V1
   ↓
JSON schema v1
```

То есть:

> входной контракт Task может развиваться независимо от контрактного результата транзакции.

---

# 37. Переходная архитектурная модель V0.X → V2

Вся ранняя эволюция сводится к следующему:

```text
V0.X
│
├── безопасные filesystem operations
├── Git state
├── checkpoint
└── rollback
        ↓
V0.4
│
└── transactional execution cycle
        ↓
TaskResult V1
│
└── structured execution result
        ↓
Task V1
│
└── задача как объект
        ↓
Task V2
│
├── task_id
├── description
├── edits
└── expected_paths
```

---

# 38. Главные инварианты, унаследованные V2

1. Agent не изменяет файл, если фактическое состояние не соответствует ожидаемому.
2. Автоматическая задача начинается только из контролируемого состояния workspace.
3. После PRECHECK создаётся checkpoint.
4. Ошибка после checkpoint запускает rollback.
5. Rollback относится ко всей Task, а не только к последнему edit.
6. Успех требует прохождения всех необходимых стадий pipeline.
7. DIFF показывает фактическое изменение, а не предполагаемое.
8. DIFF validation проверяет соответствие результата контракту.
9. Validation failure до checkpoint не требует rollback.
10. Rollback failure является отдельным опасным состоянием.
11. TaskResult всегда является структурированным результатом выполнения.
12. Task V2 не изменяет TaskResult JSON V1.
13. Multiple edits являются частью одной транзакции.
14. Несколько edits одного пути допустимы.
15. create → replace одного пути допустим.
16. `expected_paths=[]` означает отсутствие path oracle.
17. V2 является переходным контрактом к более семантической модели.

---

# 39. Граница V2

К концу V2 Agent уже умеет надёжно отвечать:

> «Какие конкретные изменения выполнить и успешно ли транзакционно выполнены эти изменения?»

Но ещё не умеет формально отвечать на более высокий вопрос:

> «Какова семантическая цель задачи, над чем именно она выполняется, какие условия должны быть истинны до начала, какой результат должен быть доказан и каким способом это доказательство должно быть получено?»

Именно эта граница приводит к Task V3.

---

# 40. Финальный переход V2 → V3

Поэтому архитектурное направление стало:

```text
Task V2
=
описание edits + базового oracle
```

↓

```text
Task V3
=
semantic task contract
```

где появляются:

```text
Intent
Target
Goal
Preconditions
Expected
Validation
ExecutionPolicy
Evidence
```

Но V3 не должен уничтожать V2.

Правильный переход:

```text
V2
   ↓
stable compatibility baseline
   ↓
V3 semantic layer
   ↓
gradual migration
```

Именно поэтому позднейшая V3-спецификация прямо сохраняет V2 compatibility mechanisms до безопасной миграции.
