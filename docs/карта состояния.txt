1. Что вообще за проект

У нас есть два связанных проекта:

SimulationAgent
        │
        │ управляет / изменяет / проверяет
        ▼
SimulationZero-Cpp

SimulationAgent — Python-агент, задача которого в конечном счёте не просто выполнять команды, а уметь принимать семантически заданную задачу, разрешать её, планировать выполнение, выполнять, собирать доказательства результата и определять, действительно ли задача достигла требуемого состояния.

Безопасное исполнение
        ↓

        ↓

        ↓

        ↓

4. Task V2

V2 — это не временный черновик, а стабильный compatibility baseline.

Главная структура:

Task
├── task_id
├── description
├── edits
└── expected_paths

edits поддерживает:

create
    path
    content

replace
    path
    old_text
    new_text
    expected_count?

Ключевые правила:

path — непустая строка;
content может быть пустым;
old_text не может быть пустым;
new_text может быть пустым;
expected_count — либо отсутствует, либо положительное целое;
bool нельзя использовать как expected_count;
несколько edits разрешены;
несколько edits могут обращаться к одному пути;
возможен create → replace того же пути.

expected_paths имеет важную семантику:

expected_paths == []
        ↓
нет path oracle

То есть пустой список не означает «изменений быть не должно».

При непустом expected_paths сравнивается точное множество изменённых путей.

23. Retry

Retry сейчас является step-level, а не повтором всей задачи целиком.

Если:

step A SUCCESS
step B FAILED

retry должен повторить:

step B

а не заново запускать A.

может остановить дальнейшее продвижение

но не убивает произвольно уже работающий Python thread.

27. Очень важное решение: TaskRun ≠ Retry attempt

У нас теперь:

TaskRun

является самостоятельным lifecycle.

Новый вызов executor:

создаёт новый TaskRun.

Поэтому:

Run #1
Run #2

независимы.

История, evidence и effective policy одного run не должны загрязнять другой.

56. Что сейчас является «истиной» проекта

Я бы установил для дальнейшей работы такую иерархию авторитетности:

1. Зафиксированный контракт
       ↓
2. Реальный production code
       ↓
3. Проверенные тесты
       ↓
4. Архитектурные решения из разработки
       ↓
5. Гипотезы

То есть если старое наше рассуждение противоречит фактическому коду — сначала проверяем, не устарело ли рассуждение.

57. Самое важное правило нашей дальнейшей работы

Не надо заново спрашивать:

«А не лучше ли нам сейчас сделать ещё одну архитектурную подсистему?»

Сначала проверяем:

что уже существует
что реально работает
что реально отсутствует

и только затем меняем минимально необходимое.
